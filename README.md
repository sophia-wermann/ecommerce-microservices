# ecommerce-microservices

A polyglot microservices architecture for an e-commerce system, demonstrating **technology independence** and **polyglot persistence** — each service uses the language and database best suited to its domain.

## Overview

This project implements two independent microservices that communicate over REST/JSON:

| Service | Language | Framework | Database | Port |
|---|---|---|---|---|
| **catalog-service** | Python | FastAPI | MongoDB | `8001` |
| **order-service** | Java | Spring Boot | MySQL | `8000` |

Each service owns its data — there are no shared databases. The `order-service` calls the `catalog-service` to validate products before placing an order, demonstrating cross-service communication between heterogeneous stacks.

## Architecture

```
          ┌─────────────────────────────────────┐
          │         Client (Postman / curl)      │
          └────────────┬──────────┬─────────────┘
                       │          │
               REST/JSON          REST/JSON
                       │          │
          ┌────────────▼──┐  ┌────▼───────────────┐
          │ catalog-service│  │   order-service     │
          │ Python/FastAPI │◄─│ Java / Spring Boot  │
          │   port: 8001   │  │     port: 8000      │
          └────────┬───────┘  └──────────┬──────────┘
                   │                     │
                   ▼                     ▼
              [MongoDB]              [MySQL]
              port: 27017            port: 3306
         (flexible documents)   (transactional data)
```

### Why polyglot persistence?

- **MongoDB for the catalog**: product attributes vary widely by category (a laptop has CPU/RAM/storage; a shirt has size/color/material). Document-oriented storage handles this schema flexibility naturally.
- **MySQL for orders**: order placement requires ACID transactions — if any step fails (create order, insert items, update stock), everything must roll back. Relational databases handle this reliably.

## Services

### catalog-service

Manages the product catalog with a flexible schema per product category.

**Endpoints:**

| Method | Path | Description |
|---|---|---|
| `GET` | `/products` | List all products (supports `?category=` filter) |
| `GET` | `/products/{id}` | Get product by ID |
| `POST` | `/products` | Create a new product |
| `PUT` | `/products/{id}` | Update a product |
| `DELETE` | `/products/{id}` | Delete a product |

Interactive docs available at `http://localhost:8001/docs` (Swagger UI auto-generated by FastAPI).

**Example product documents:**

```json
// Electronics
{
  "name": "Dell Inspiron 15",
  "category": "electronics",
  "price": 1299.99,
  "stock": 15,
  "attributes": {
    "processor": "Intel Core i5 12th Gen",
    "ram": "8GB DDR4",
    "storage": "256GB SSD"
  }
}
```

```json
// Clothing
{
  "name": "Basic Cotton T-Shirt",
  "category": "clothing",
  "price": 29.99,
  "stock": 100,
  "attributes": {
    "sizes_available": ["S", "M", "L", "XL"],
    "color": "Black",
    "material": "100% Cotton"
  }
}
```

### order-service

Handles order creation and lifecycle management with full transactional support.

**Endpoints:**

| Method | Path | Description |
|---|---|---|
| `GET` | `/orders` | List all orders |
| `GET` | `/orders/{id}` | Get order with its items |
| `POST` | `/orders` | Create order (validates product via catalog-service) |
| `PUT` | `/orders/{id}/status` | Update order status |
| `DELETE` | `/orders/{id}` | Cancel an order |

**Order status flow:** `PENDING` → `CONFIRMED` → `SHIPPED` → `DELIVERED` (or `CANCELLED`)

**Database schema:**

```sql
orders        (id, customer_name, customer_email, status, total_amount, created_at)
order_items   (id, order_id, product_id, product_name, quantity, unit_price)
```

`product_id` stores the MongoDB ObjectId from the catalog, linking both databases at the application layer without tight coupling.

## Getting Started

### Prerequisites

- [Docker Desktop](https://www.docker.com/products/docker-desktop/) — required to run all services
- [Git](https://git-scm.com/)

### Run with Docker Compose

```bash
# Clone the repository
git clone https://github.com/sophiawermann/ecommerce-microservices.git
cd ecommerce-microservices

# Start all services (databases + microservices)
docker-compose up --build

# Stop all services
docker-compose down
```

Services will be available at:
- Catalog Service (Swagger UI): http://localhost:8001/docs
- Order Service (Swagger UI): http://localhost:8000/swagger-ui/index.html
- MongoDB: localhost:27017
- MySQL: localhost:3306

### Run services individually (development)

**catalog-service:**
```bash
cd catalog-service
python -m venv venv
source venv/bin/activate      # Linux/macOS
venv\Scripts\activate         # Windows
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8001
```

**order-service:**
```bash
cd order-service
mvn spring-boot:run
```

## Key Design Decisions

**1. Database-per-service** — each microservice owns its database exclusively. No shared schema, no cross-service joins. This enforces loose coupling at the data layer.

**2. Synchronous REST communication** — the order-service calls the catalog-service via HTTP to validate product existence and price before persisting an order. This keeps the integration simple and observable.

**3. Denormalized order items** — `product_name` and `unit_price` are copied into `order_items` at creation time. This ensures historical accuracy: if a product's price changes, past orders remain correct.

**4. Technology heterogeneity** — Python and Java are intentionally chosen to demonstrate that microservices can be independently built, deployed, and scaled regardless of language, as long as they agree on the HTTP/JSON contract.
